# Product Flow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the single-shot "watch seven agents" demo with a product flow: chat with a Brief agent (≤1 question round) → 3 option cards with rough cost → full reviewed plan with booking links for the card the user opens.

**Architecture:** Two stateless SSE endpoints (`POST /api/options`, `POST /api/plan`); the browser carries the brief and chosen option between them. Agent runtime (`agent.py`) is untouched; schemas, agent definitions and orchestration change. Booking links, status lines and cross-agent checks are deterministic code in small new modules.

**Tech Stack:** Python 3.12, raw `anthropic` SDK, FastAPI + sse-starlette, Pydantic v2, vanilla JS single `index.html` with vendored Leaflet/fonts, pytest (dev only).

**Spec:** `SPEC-product-flow.md` (delta) against `SPEC.md` (baseline). Mockup: `docs/mockups/product-flow.html` (option A, ring).

## Global Constraints

- No agent framework (no LangChain/LangGraph). `backend/agent.py` is not modified.
- Backend modules use flat imports and are run from `backend/`; every module starts with `from __future__ import annotations` and a docstring saying why it exists.
- `run_tool` never raises; every `tool_use` gets a `tool_result` (unchanged runtime guarantees).
- Runtime `requirements.txt` unchanged. `pytest` goes in new `requirements-dev.txt` only.
- Frontend: one `frontend/index.html`, vanilla JS, no build step, `esc()` on every model-supplied string, keep palette tokens and Fraunces/Manrope fonts. Never edit `frontend/vendor/`.
- Never shown to end users: tool names, thoughts, JSON, scores, token counts, reviewer notes.
- Booking URLs are built only by `links.py` from validated fields; the model never writes URLs.
- Recordings (`demo/*.jsonl`) are regenerated by `python demo/make_demo.py`, never hand-edited. V1 assertions are kept, not weakened.
- Cards: exactly 3, best match first. Brief: at most 1 question round.
- Chat request limits: ≤ 8 turns, each ≤ 1000 chars, last turn role `user`.

## Review Focus

1. **Accented / differently-cased town names** ("Samara" vs "Sámara", "santa teresa") between itinerary and stays must not count as a mismatch → `checks._norm` casefolds and strips accents (Task 2 test `test_accent_and_case_insensitive_match`).
2. **Names with apostrophes, ampersands, commas, non-ASCII** in links must be URL-encoded, and in HTML escaped → Task 3 test `test_stay_url_encodes_special_characters`; Task 9 step uses `esc()` for every card/plan string.
3. **Tampered or malformed request bodies** (nights not matching dates, empty transcript, 9 turns, last turn from assistant, bad airport code) must return 422, never 500 or a started run → Task 1 `test_brief_nights_must_match_dates`, Task 6 `test_bad_bodies_are_422`.
4. **User clicks a second card while one is planning, or navigates away** → only one plan stream at a time: other "Plan this trip" buttons are disabled while a plan streams; the stream's `AbortController` is aborted on "Start over" (Task 9 manual check).
5. **Judge returns a pick/ranking that doesn't match option names** → fallbacks still yield 3 cards, exactly one `best` → Task 5 `test_rank_options_fallbacks`.
